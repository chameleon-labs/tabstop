Format: **date · decision · why · what was rejected/deferred**.

## 2026-08-02 — the frontend shares a type-only contract package, not the server's internals

`web/` exists, and with it the question the backlog had been deferring: three surfaces consume the audit response — live progress, audit detail and the share page — and none of them may keep their own copy of its shape.

**A pnpm workspace at the repository root, with `contract/` as a third project.** `@tabstop/contract` publishes an `exports` map containing a `types` condition and *nothing else*, so there is no runtime entry to import. Both failure modes were checked by doing them rather than assumed: add a value export there and import it, and `vite build` cannot resolve the specifier while Node refuses it with `ERR_PACKAGE_PATH_NOT_EXPORTED`. Importing one of the types as a value is a different mistake caught earlier — `verbatimModuleSyntax` is on in every project, so it is TS1484 before it is anything else. Nothing from this package can reach a browser bundle by accident.

**Rejected: importing types straight out of `server/src` behind a path alias.** It needs no infrastructure and works today, which is genuinely appealing. But `import type` erasure only protects the *bundle*; it does nothing about the coupling. `web/`'s typecheck would compile files under `server/src`, so the frontend would break on server refactors that changed nothing about the wire, and there would be no boundary saying which server types are published and which are internal. **Rejected: OpenAPI codegen.** The most robust option and the right one eventually; it is a great deal of machinery for four endpoints, and it can be adopted later without unpicking anything below.

**The contract redeclares its types rather than re-exporting the domain's, and that is forced rather than sloppy.** `domain/` may import nothing but relative paths — `architecture.spec.ts` asserts it — so a domain model cannot live in a package, and `contract/` sits below the server so it cannot import one either. The redeclaration is only safe if drift is impossible, so `presentation/helpers/contract-proof.ts` asserts mutual assignability for each shared union and struct, and the server's typecheck fails when either side moves without the other.

**A return-type annotation is not that proof, which is the part worth remembering.** It checks one direction, and one direction misses both ways this response widens by accident: `countsByImpact` is a `Record`, and a record over a *wider* key union is assignable to one over a narrower union — excess property checking would object, but it only applies to fresh object literals and this value is not one; and `nodes` is passed through by reference, so a field added to the domain's `ViolationNode` reaches the wire with no literal to check it against. Both compile cleanly under an annotation. Adding a fifth `Impact`, and adding a field to `ViolationNode`, were each run against the real typechecker to confirm the assertion fires and names the type that moved.

**`toAuditResultResponse` stays in the server.** Only transport types moved. That mapper is a security boundary — `AuditModel` carries `pageId`, which links to a site and therefore to an account — and it has a spec asserting the forbidden keys are absent. `architecture.spec.ts` now also pins the exact list of files allowed to name `@tabstop/contract`; the list is expected to grow by one view helper per published endpoint, and a controller or adapter appearing in it is the signal that a wire type has started being used as an internal model.

**The workspace has costs, and they were paid rather than deferred.** `pnpm-workspace.yaml` and the lockfile moved to the root, `server/`'s `packageManager` field was dropped so there is one declaration of it, and Server CI's install now covers `web/`'s dependencies too. That last one is deliberate: `--filter` would install a different tree from the one a developer has, and that difference is precisely the sort of thing that only ever surfaces as a CI-only failure. The path filter gained `contract/**`, because a change there can break the server's build while touching nothing under `server/`.

**`web/` has no CI yet** — #18 — so nothing runs its 29 specs on a pull request. They pass locally and each was mutation-checked; that is the honest state until #18 lands.

## 2026-08-02 — provider backoff is a monotonic queue-wide deadline

BullMQ's manual `Queue.rateLimit` writes its limiter key with `SET ... PX`, so
the latest caller replaces the existing TTL. That is unsafe across alert worker
replicas: a short ordinary rate-limit response can arrive after a daily-quota
response and reopen provider traffic hours early.

Alert delivery now installs backoff with one Redis Lua transition equivalent to
`max(current TTL, requested delay)`. Every path writes BullMQ's exact
manual-limiter sentinel: this matters because the same key can hold an ordinary
throughput counter below the worker's maximum, and extending that counter's TTL
would not pause anything. A longer finite expiry is kept, a shorter one is
extended, and a non-expiring key remains non-expiring. The script uses the
queue's existing client and public limiter key, preserving its name and prefix
without another connection, a read-then-write race, WATCH retries, or a lock
key.

The processor awaits that transition before throwing BullMQ `RateLimitError`,
which returns the job without spending a normal attempt. If Redis cannot
install the shared delay, that failure propagates instead: claiming a safe
rate-limited retry when other replicas remain free to send would be false.
Effective-TTL metrics and policy changes remain deferred because no caller
currently needs them.

## 2026-08-01 — deterministic HTTP route specs use per-app dependencies

- HTTP route specs receive complete per-app dependencies: a fresh in-memory
  limiter and recording audit queue. Real Redis/BullMQ behavior remains in
  adapter integration specs.
- Successful rate-limit decisions own an idempotent refund bound to the
  adapter and cost that produced them. Changing fallback degraded state
  cannot redirect a refund.

The five-second degraded window deliberately does not reconcile historical
token counts between Redis and memory. It bounds the outage behavior from the
point of fallback; attempting to merge prior histories would make the fallback
state depend on unavailable Redis state and undermine that guarantee.

## 2026-07-31 — Resend for regression alerts, with Postgres as the outbox

Regression alerts use **Resend's HTTP API**. The volume is tiny, so provider price is irrelevant beside deliverability and operational surface. Resend has the smallest API for a plain-text message today and leaves a clean path to React Email if HTML ever earns its cost. Postmark was the strongest rejected alternative — excellent transactional deliverability, but no advantage this feature currently uses. SES was rejected because its lower unit price buys nothing at this volume and its account, IAM and reputation setup are materially heavier. The adapter calls HTTP directly rather than adding an SDK whose only work here would be one `POST /emails`.

Sending is opt-in. `MAIL_DRIVER` defaults to `console`; only the explicit `resend` value can construct the network adapter, and that mode fails startup without `RESEND_API_KEY`. Local and test runs therefore cannot mail a real recipient by forgetting to turn something off. Console returns a distinct `previewed` outcome: it logs the message but does not stamp `emailed_at`, because no provider accepted anything. When Resend is enabled later, the dispatcher is allowed to revive the retained completed preview job so the still-unsent database event is delivered immediately.

**The database event is the outbox; Redis is not the record of work.** A minute-level BullMQ scheduler pages through every `alert_events` row whose `emailed_at` is null and `failed_at` is null and enqueues a deterministic job id. Overlapping dispatchers collapse to one job. A queue outage leaves the row untouched for the next minute, and a provider failure retries the same event rather than running regression detection again. `emailed_at` is a conditional update after provider acceptance only. BullMQ retains an exhausted failed job for a day and treats an `add` with its id as a harmless duplicate; without an explicit revival that retention would block the database event rather than protect it. The dispatcher therefore reprocesses a retained failed job and resets its attempt counters.

**Terminal delivery state belongs on the event row, not in an operator's memory.** `previewed_at` is claimed conditionally before the safe console adapter writes. That ordering deliberately chooses at-most-once behavior: overlapping workers cannot both emit, while a crash after the database claim may omit the local preview. It does not claim provider delivery, which is why a later real-provider run may still stamp `emailed_at`. `emailed_at` means a provider accepted the message and the event is done. `failed_at` paired with `failure_reason` means delivery reached a deliberate terminal stop and the minute dispatcher now excludes the row instead of replaying a known-bad send forever. That makes the recovery action explicit and reviewable: after the operator repairs the underlying configuration, they clear only the terminal failure fields on the events they have chosen to retry:

```sql
update alert_events
set failed_at = null, failure_reason = null
where id = $1 and emailed_at is null;
```

No public retry endpoint was added. A retry is an operational judgment about what was repaired and which failures are safe to replay, and a deploy is exactly the wrong moment to guess that predicate. Bulk retry therefore stays a deliberate operator-chosen SQL filter and must never run automatically on deploy.

The Resend request also carries `Idempotency-Key: alert-event/<id>`. That closes the common uncertain-outcome window where Resend accepted the message but the worker lost the response or failed before the Postgres update: repeating the request returns the original result for 24 hours. It is not described as mathematical exactly-once delivery — no transaction spans Resend and Postgres, and a database outage lasting beyond that window can still duplicate a send. The durable event, deterministic queue id and provider key are the strongest available composition without introducing a mail relay we operate ourselves.

**Unsubscribe disables alerts, not monitoring.** Setting `monitoring_enabled=false` would make “stop emailing me” silently stop the daily checks and destroy the future trend, a materially larger action than the user requested. Migration 008 adds `pages.alerts_enabled`; detection checks it before creating new events, the dispatcher excludes disabled pages, and an already-queued send checks it again before contacting the provider. Existing events stay as detection history with an honest null `emailed_at` rather than being deleted or falsely marked sent. The token is `v1.<page id>.<HMAC-SHA256>`, signed with a separate deployment secret. The id is visible but the authority is unguessable, page-scoped and timing-safe to verify.

The RFC 8058 endpoint accepts unauthenticated form POSTs and messages include both `List-Unsubscribe` and `List-Unsubscribe-Post`. A browser GET displays a confirmation form and does not mutate state, because mailbox security scanners prefetch links. Provider-level click rewriting stays off; the page-detail link carries `utm_source=alert_email`.

**DNS remains a deployment action, not something this repository can fake.** Resend recommends a dedicated sending subdomain; its verification supplies SPF and DKIM, while DMARC is published on the organizational domain and tightened only after monitoring. No SPF, DKIM or DMARC records were visible for the intended Tabstop sending domain on 2026-07-30. The server runbook records the exact verification and real-inbox checks, and production must not select `MAIL_DRIVER=resend` until they pass.

## 2026-07-31 — a connection still opening is not an outage, and quiet tests are a feature

The rate limiter degraded on the first request every process served, and had done since #8. Its client is built with `enableOfflineQueue: false` — the option that makes a dead Redis reject rather than hang, which is what the whole degrade-don't-refuse design rests on — and **ioredis draws no distinction between dead and not yet connected.** A socket takes a few milliseconds to become writable; until it does, every command fails with "Stream isn't writeable and enableOfflineQueue options is false". So the first request lost a race it should never have been in, and `FallbackRateLimiter` then served the next five seconds from a per-process bucket instead of the shared one.

**Deterministic, not a flake.** Constructing the client and issuing a command in the same tick reproduces it every time, locally, with the exact message CI logs — which is also why it looked like a CI-only problem: locally the first request usually arrives late enough to win.

`RedisTokenBucket` now waits for the connection before its command. ioredis offers unbounded queueing or none, so this is the middle: queue briefly, then fail. A second is far longer than a connection needs, and an outage costs one wait per degraded window rather than one per request, because the first failure moves the limiter onto its fallback for five seconds. `end` fails immediately, since a closed client will never be ready.

**The wait is shared across a burst**, for the reason `CoalescingDnsResolver` coalesces and one more this class cannot avoid: each wait attaches `ready` and `error` listeners, and Node warns past ten. A burst arriving at startup — which is exactly when a connection is still opening — printed `MaxListenersExceededWarning` to stderr, reintroducing the noise the change exists to remove. Caught in review; confirmed by removing the coalescing, which prints *"11 ready listeners added to [Commander]"*. The shared promise is cleared on settlement rather than memoised, so a client that dropped and reconnected waits for its own `ready` instead of remembering the last one.

Rejected: waiting once at startup instead. It is the obvious shape and it fixes only production — every route spec builds the app directly rather than through `server.ts`, so the half of this that made rate-limit assertions unreliable would have survived. A fix that a caller has to remember is one the tests do not get.

**The three expected log lines are now silenced and asserted** in the specs that cause them. They were never bugs: a stubbed limiter throwing, a stubbed primary refusing, and the session sweeper reporting a pass that found nothing — the last of which is deliberate, since a maintenance task that only speaks up when it has work is one nobody notices has stopped. The cost was not the noise itself but that it read exactly like the genuine degradation above, which is how that one survived so long unexamined. Silencing without asserting was rejected outright: it would delete the only cover those decisions have.

**Not claimed:** that this fixes the `account-routes.test.ts` flakes. Eight baseline runs on `main` and six on the branch all passed, so the local signal is too weak to confirm or rule it out; CI is where it showed. Recorded on #50 rather than asserted here.

## 2026-07-30 — regression means a comparable earlier result, and completion owns its alert

A tracked audit now emits an `AlertEvent` when its score falls by the account threshold or it gains a `serious`/`critical` rule. It emits at most one signal: a new severe rule wins over a simultaneous score drop because it says what became actionable, while the score can only say that the aggregate moved. Improvements, first audits and anonymous audits do not alert.

**Rules are compared by id, not by nodes or severity transitions.** The same rule moving to a different selector is still the same finding, and a rule already present as `minor` becoming `serious` is not “new”. `diffViolations` owns that set arithmetic and returns current objects for `added`/`unchanged` and previous objects for `fixed`, so #22 can show richer rows without rebuilding a definition that might disagree with email. An alert stores the two audit ids rather than a frozen copy of the diff for the same reason.

**An axe-version change suppresses the whole alert.** A release may add or reclassify rules, and presenting that as the page regressing would alert every monitored page after an engine bump—the fastest way to teach users to ignore the product. The history endpoint already returns `axeVersion`, so the UI can explain the discontinuity without pretending it came from the page. Alerting with an engine-update caveat is deferred; v1 chooses the conservative signal.

**“Previous” means the latest earlier completed audit, not the result that most recently happened to finish.** Workers can complete out of order. The baseline query is bounded below the current `(created_at, id)`, ordered by that same tuple descending, and filters `status = done`; a failed audit is not a score of zero, and an audit created later cannot become this one's past. The id is the tiebreak because Postgres `now()` is transaction time and rows can share a timestamp.

**Completion and detection are one transaction.** Marking the audit `done` and then inserting its alert in a separate step leaves a fatal gap: the worker can crash between them, and every redelivery sees a terminal audit and acknowledges it, so the alert is lost forever. The existing claim-fenced update now gates the transaction; if it updates no row, the stale attempt writes neither result nor event.

The issue sketched catching the daily unique violation. That is not safe inside this transaction: once Postgres raises `23505`, the transaction is aborted, and “handling” it would still roll the valid completion back unless a savepoint were introduced. The insert instead names `alert_events_one_per_page_per_day`'s exact expression as its `ON CONFLICT DO NOTHING` target. The race becomes a normal no-op without swallowing foreign-key or check failures, and the completion commits. The UTC day keys on detection, not delivery, so an unsent event still spends the page's one alert for that day.

## 2026-07-30 — the nightly re-audit, and dedupe on intent rather than on a timestamp

Every page with `monitoring_enabled` is audited once per UTC day, fanned out at 02:00 UTC by a BullMQ job scheduler in the worker and spread over a six-hour window. This is the promise the product is actually making; without it tabstop is a one-off audit tool with an account system.

**A job scheduler, not a timer — and the reason is the opposite of the session sweeper's.** That sweeper is deliberately a `setTimeout` loop because #10's design turns on authentication not depending on Redis. Nothing of that argument transfers here: this job's entire output is BullMQ jobs, so Redis is already on its critical path, and a timer fires once *per worker replica* — N fan-outs racing over the same rows every night. The schedule lives in Redis and fires once however many workers are running. The sweeper stays where it is; the comment on #13 asking this scheduler to adopt it predates #45, which already shipped it.

**Jitter is deterministic per domain, and it is FNV-1a rather than sha256.** Random jitter spreads the load equally well and moves every page's audit time every night, so a page's own trend line would compare Monday morning against Tuesday evening — for a product whose whole output is "did this get worse", a measurement whose conditions wander is worth less than one taken at a consistent hour. The hash is not a security primitive (knowing which minute your own page is audited buys nothing), and `domain/` may import nothing at all, not even `node:` builtins — so a pure 32-bit hash keeps the boundary and the offset both. The domain sets a base offset and the page picks a stagger slot within it, so pages sharing a host are separated while the host still lands where it always lands.

**Both halves come from identity, never from position in the run — and the first version got that wrong.** It numbered a domain's pages by the order the worklist returned them, which is not a property of a page at all: it shifts when a sibling is added, paused, or still mid-audit, and a retry — which sees only the pages the previous attempt failed on — restarts the numbering at zero and hands a page the slot a sibling already occupies. So "the same slot every night", the entire reason this is a hash rather than `Math.random`, held only for domains tracking exactly one page. The slot is now `hash(pageId) mod slots`. What that gives up is the guarantee that two same-domain pages sit a whole stagger apart — they now collide a few percent of the time, and at `AUDIT_CONCURRENCY` above one those two really can reach the same host together. That is acceptable because per-origin serialisation was never this function's job: it spreads the night's work and holds each page at a consistent hour, and #41 owns making sure two audits of one host never overlap, at the worker, which is where it has to be since a delay can only separate jobs that start on time.

**The dedupe index keys on a new `scheduled_for` column, not on `created_at::date` as #13 sketched.** That sketch could not be created at all — `timestamptz::date` is STABLE, not IMMUTABLE — which is the same wall #4 hit on `alert_events` and is the least interesting problem with it. Pinning the zone to fix that still leaves a constraint that counts audits nobody scheduled, so a manual re-audit would be refused because the nightly run had already happened; the issue flagged that cost and asked for a decision, and this is it. Recording the run's day explicitly also makes the day a property of the **run** rather than of the insert: a fan-out starting at 23:59:59 stamps one date, where deriving it per row splits it across two and lets both halves insert. The column is write-only — node-postgres parses a `date` at *local* midnight, so reading it back would mean something different depending on where the process runs.

**Idempotency is two layers, and the gap between them is left open on purpose.** The eligibility query skips pages with work in flight or an audit created since midnight UTC; that is cheap and catches every ordinary case, and it is also check-then-act, so two overlapping runs both select a page before either inserts. The partial unique index is what makes the promise true. Papering over the window with a lock would have made the constraint decorative — instead `addScheduled` returns null on conflict and the run counts it as *skipped*, not failed, because an overlapping run is the second layer working rather than a broken night.

**`backlogCount` stopped counting delayed jobs, and this issue is why.** It counted `waiting` and `delayed`, on a premise its own comment stated: nothing enqueues an audit with a delay of its own, so a delayed job could only be one inside its retry backoff. The fan-out breaks that by design. Left alone, a hundred monitored pages would push the depth over `AUDIT_QUEUE_MAX_DEPTH` the instant the run fired, and `POST /api/audits` — the product's hook — would answer 503 for six hours every night against idle workers. That is not a bound failing safe, it is a bound measuring the wrong thing. What is given up is the retry-backoff window, which undercounts: the direction the old comment already argued an imprecise cost control should be wrong in. **The value of writing the premise down is that its expiry was visible.**

**A plan assertion was attempted for the new in-flight index, and dropped — the honest result.** The obvious spec (seed a page with thousands of audits, EXPLAIN the fan-out, assert it reads almost none of them) passes alone and fails in the suite: 7,635 rows against a threshold of 1,000, not a flake. The eligibility query is global, because the nightly run audits everyone's pages, so it also evaluates every fixture the parallel spec files are creating — and once the outer side is a few hundred pages Postgres correctly stops probing per page and hash anti-joins the whole table instead. The assertion was pinning the size of the shared fixture set. Same lesson as #12's lateral: **an index makes a cheap plan available, it does not guarantee one.** What can be pinned is that the index answers the predicate at all, so that assertion sits next to the migration, on one page and one predicate, where the shape is fixed.

**Two test-tooling defects found on the way, both of which made an assertion weaker than it read.** `explainRowsRead` counted `Actual Rows` only, so it measured output rather than work — and an `exists` check that scans a page's whole history and filters on status returns zero rows while reading all of them. It now adds `Rows Removed by Filter`; without that, "this reads fewer than N rows" was true of the plan it was meant to catch. And `architecture.spec.ts` matched `[^\n;]*?` between `import` and `from`, so it saw only single-line imports — 109 of the codebase's 967 specifiers were invisible to the layer rules, which in a codebase that wraps constantly is not a rounding error. Review then pointed out that fixing the newline case still left two forms out: a side-effect `import './x.js'`, which has no clause to match, and a dynamic `import('./x.js')`, which is not a statement and can sit anywhere in a file. Both carry the same coupling, so either would have let a source bypass every rule by writing its import differently. The scanner reads all three forms now, and the layer rules still turn up no violations — which is luck rather than evidence, since nothing was checking.

**Deferred:** forwarding the run summary to PostHog (#25) — the structured line is emitted and logged, including on nights with nothing to do, because a summary that only appears when there is work is one nobody notices the absence of. Per-user cadence and timezone stay out: "daily" means every 24h in UTC and the docs say so, because "daily in the user's timezone" is a per-user schedule.

**Three corrections from the #49 review, two of which change behaviour rather than only its description.**

**A capped run was not "every enabled page per day", and the cap is gone.** The first version fetched one batch of 5,000 and reported `truncated` if it filled — so anything past that went unaudited, and because the cut is by page id it is the *same* tail every night: those accounts stop being monitored while the run reports success. It now pages with a keyset cursor until the batches run out. Keyset rather than an offset because the run mutates what it is paging over — every page it schedules gains an audit in flight and leaves the predicate, so an offset would step over exactly as many pages as the previous batch handled. `truncated` survives as a circuit breaker at 50,000 pages, which means the eligibility predicate is broken rather than that the product got popular. The old flag was unsound on its own terms too: a batch that comes back exactly full proves nothing, so the query now returns one row more than the run intends to use and the answer comes from the database rather than from an inference.

**A `queued` audit row that no job will ever run used to end a page's monitoring permanently.** The eligibility query excluded pages with work in flight, with no floor on how old that work could be — so if an enqueue failed *and* the cleanup delete failed, the row survived and the page was absent from every future night, silently, with nothing failing anywhere. Retrying the delete would not have helped: the outage that failed it fails the retry. The fix has to be to stop trusting the row, not to try harder to remove it.

**The first attempt at that was wrong, and a second review round caught it.** Ageing unfinished audits out of the eligibility query after a fixed interval looks equivalent and compounds under load: once the queue stops draining inside the interval — which at one concurrent audit and 45 seconds each is around 1,900 pages a day — every *real* pending audit is old too, so its page is scheduled again on a new date the unique index happily permits, and each night adds work on top of a backlog the workers are already behind on. **Age cannot answer "is this work still live"; only the queue can.** So the eligibility query went back to excluding unfinished audits regardless of age, and a reclaim pass runs before the worklist: old rows are *candidates*, and a candidate is retired only once the queue confirms its job is gone. The age is a filter on how much gets examined, not a verdict, which frees it to be generous.

The reclaim marks the row `failed` rather than deleting it — the audit is a fact, the page was due and nothing ran it, so the dashboard should show a failure and the trend chart should keep a scoreless point. It fails **closed** on an unreachable queue, which is the opposite of the same lookup in `audit-submission.ts`, deliberately: there an unanswerable queue costs one stray job that fails once and is gone, here it would mark live audits as abandoned and schedule duplicates, so a Redis blip during the nightly run would manufacture work out of healthy rows. `abandonedReclaimed` is in the run summary and is expected to be zero; a number that keeps climbing means enqueues are being lost, which is worth knowing long before anyone notices their pages stopped being checked.

**Two follow-ups from a third review round, both worth recording.** The queue lookup that decides whether a candidate is abandoned was wrapped in a `try/catch` and documented as failing closed — which it did not, for the case that matters. An unreachable Redis does not reject, it hangs; BullMQ retries the connection forever, and `audit-submission.ts` had already measured that at five minutes with no resolution. Unbounded, one dead candidate would stall the whole fan-out until the job timeout, and the lookup would still be pending afterwards, free to resume and mutate rows outside the attempt that was supposed to have ended. It is bounded now by the same helper the submission path uses, and a timeout counts as "still held". **A `catch` is not a timeout, and writing "fails closed" in a comment does not make it so.**

**A fifth round found three more claims that outran their mechanisms, which by now is the pattern worth naming: every defect in this feature after the first has been a comment promising a guarantee the code did not deliver.** The reclaim pass asked the queue `has()`, which answers "a record exists" — but terminal jobs linger, `removeOnFail` for a day and lazily beyond that, so an audit whose job died without writing a status kept its page out of the worklist for as long as the record survived. `isPending()` asks the question that was meant: is anything still going to run this. The two callers genuinely want different questions — submission asks "did my add land", where a job that already ran must answer yes — so both methods exist and each says why. The bounded lookup then converted an unreachable queue to "still held", which left `reclaimFailures` at zero: the exact ambiguity that counter had just been added to remove, rebuilt one level down. It returns a third state now. And the jitter's collision argument rested on the worker running one audit at a time, which is only the *default* — `AUDIT_CONCURRENCY` goes to 16. Per-origin serialisation was never this function's job; it is #41's, at the worker, and the hostname key here does not even group subdomains the way #41 must.

**A sixth round found the same thing in the schema.** One partial index on `(page_id, created_at)` was documented as serving both the per-page eligibility probe and the reclaim pass's global "oldest unfinished audits" scan. It cannot: with `page_id` unconstrained Postgres has no ordered path through that index, so it reads the entire live set and sorts before applying the limit. Measured by putting the leading column back: 2,009 rows read instead of ten. Harmless while few audits are unfinished, and useless exactly when many are — which is when a stale backlog exists and the reclaim pass is the thing meant to clear it. Two partial indexes now, one per access pattern, each cheap because both hold only live rows. The spec that used to name the index by hand went with it: a second partial index over the same rows made the planner pick the other one, correctly, and the row count was always the real assertion.

**A seventh round found the reclaim pass could starve, which would have made it decorative.** It took one first batch of the oldest candidates. `created_at` never changes, so candidates that are old but *legitimately pending* hold the front of that list every night — the normal state of a queue that has not drained inside the stale window — and an orphan behind them would never be examined, leaving its page excluded from re-audits permanently. That is the exact failure the pass exists to prevent, so a version of it that can be starved is a version that quietly does not work. It pages now, with a `(created_at, id)` cursor: the tiebreak is load-bearing because `now()` is transaction time, so a fan-out's rows share a timestamp, and a cursor that cannot distinguish them steps over one. Bounded by the same per-run ceiling as the worklist, since each candidate costs a Redis round trip.

**And an interrupted run reported no counters at all.** The aborted log line carried a reason and nothing else, so a night where earlier batches scheduled pages before something threw had no record of how many — and the retry's own summary covers only the tail, so nothing reconstructs it. The run publishes a snapshot after the reclaim pass and after every batch; the worker keeps the last one and logs it on the error path. A copy each time rather than the live object, or the caller would hold a reference that kept changing under it and report a number the run had not reached when it failed.

**An eighth round found the cursor was not strictly after the row it came from.** Postgres keeps `timestamptz` to microseconds; node-postgres parses it into a JavaScript `Date`, which holds milliseconds. So a cursor built from the parsed value sits just *below* the row it was taken from, `created_at > cursor` is true of that row, and the next batch serves it again — measured, and with a small batch it repeats until the run's ceiling is spent while the abandoned audits behind it are never reached. Rounding instead of truncating would only move the error to the other side, where a row in between is skipped, which is worse. The cursor now carries the timestamp as the text Postgres itself rendered, cast back explicitly, and the protocol says it is opaque. Written as raw SQL because Kysely's typed tuple builder requires the value to match the column's *parsed* type — the Date whose precision is the problem.

The same round found the import scanner still missing `import(specifier, { with: … })`, since the pattern required the call to close immediately after the specifier. Worth recording what the suggested remedy turned up: **the TypeScript parser is not available here.** TypeScript 7 is the native port and exposes no `createSourceFile`, so there is no AST to walk without adding a second parser to a spec. That makes the scanner an enumeration rather than a guarantee, and after three rounds of it being incomplete the comment now says so instead of claiming totality.

**Also recorded rather than fixed:** `runWithTimeout` bounds the attempt, not the work. Nothing passes a signal down to Kysely and the pool sets no `statement_timeout`, so a lock-stalled query keeps its connection and its handler can resume after BullMQ has started the retry. What bounds the damage is the unique index and the fenced writes, not the timer — for both the fan-out and the audit worker, which have had this exposure since #5. That is a process-wide gap, so it is #52 rather than a patch here, and the comments that used to call it a hard stop now say what it actually stops.

**A fourth round then found the observability claim was false for the case it most mattered in.** `runWithTimeout` rejects once its bound fires, discarding whatever the handler returned — so a run stopped by the 30-minute timeout produced no structured record at all, however cooperatively it had finished. There are two deadlines now: a soft one the run honours, so it stops at its next page and *returns* a summary that gets logged, and the hard `runWithTimeout` bound a minute later for a run wedged somewhere that checks no signals. Both paths emit a record, tagged `completed` or `aborted`. The same round pointed out that `reclaimAbandoned` returned a bare number, so "nothing needed reclaiming" and "I could not look" were the same value — which would have hidden a reclaim pass that had stopped working behind a healthy-looking night, reintroducing one level up the exact silent degradation the pass was added to prevent. `reclaimFailures` is now its own counter.

And a truncated run — one that hit the circuit breaker with pages still due — was logged and nothing else, so the job completed successfully. A background job that did not do the work it promised and reports success is missing from every queue dashboard there is. It now fails, which also makes the retry useful rather than a formality: every page the attempt scheduled has an audit in flight and drops out of the worklist, so the next attempt starts on the tail instead of repeating the head. A run cut short by *shutdown* still reports success, because failing it would only spend attempts on retries the departing worker cannot serve.

**The fan-out is abortable, because it is far longer than the shutdown grace.** The worker's force-exit timer is sized around one audit's budget, and a full run is minutes of sequential inserts and enqueues — so a SIGTERM mid-run reached the force exit, and a hard exit can land between creating an audit row and queueing its job, stranding exactly the row above. `shutdown` now aborts the run, which stops at its next page; the remaining pages are simply unscheduled, which is what the next run is for. A run cut short this way is deliberately not a failure, since failing the job would spend its retries on a worker that is going away.

**The recurring-job registration had no test at all.** Every scheduler spec drives the usecase directly, so a cron that never fires, a dropped timezone, or a template that lost its retry options would all have shipped green. Covered now against real BullMQ by reading the schedule back out of Redis, including that a second upsert updates in place — if it added instead, a deploy that changed the cron would leave both schedules registered and the fan-out would fire twice a night, which the day-scoped unique index absorbs silently.

**Left as it is, with the reason recorded:** `backlogCount` cannot distinguish a retry backoff from a scheduled delay, because BullMQ puts both in `delayed`. Against a handler that fails fast, the queue can hold roughly `attempts` times the cap in work that is coming back. It is bounded, it errs toward accepting rather than refusing, and it is now pinned by a spec rather than left as a claim. Fixing it properly means moving the scheduler's delay off the audit queue entirely, which is #51 — a design change wanting measurements, not a patch on a shipping branch.

## 2026-07-30 — page history, and a `days` parameter that clamps but does not guess

`GET /api/pages/:id/history?days=90` — the data behind the trend chart (#21).

**Failed audits are points, flagged, with `score: null`.** Dropping them makes an outage look like continuity; coercing them to zero makes it look like a catastrophic regression. A gap is information, and "your site was unreachable for three days" is exactly what a monitoring tool should be able to say. `axeVersion` rides on every point for a related reason: a score shift across an axe upgrade is not a regression in the page, and without a marker the chart raises a false alarm the first time axe is bumped — which is how a team learns to ignore it. Points come back ascending so the chart renders in array order, which is the opposite of what `order by created_at desc` habit produces.

**`days` clamps at 365 but a non-integer is still a 400.** The two are different kinds of wrong. `days=100000` is a coherent request for more than we will serve — and an unclamped one is a free table scan for whoever asks — so it is answered with a year, and the response echoes `days` back so the clamp is visible rather than a silent truncation. `days=lastweek` is not a request that was understood at all, and clamping it would mean picking a number on the caller's behalf and pretending they asked for it.

**Cacheable, `private`, and `Vary: Cookie`.** A finished audit is immutable and a monitored page gains at most one point a day, so a minute of staleness is invisible while the repeat-visit cost goes to zero. `private` rather than the share page's `public`, because this is owner-scoped data behind a session; `Vary: Cookie` because the URL alone does not identify the response, and two accounts on one browser must not share a cache entry for `/api/pages/1/history`.

**The index is asserted, not assumed.** The read is a single scan of `audits_page_created_idx`, which is declared `(page_id, created_at desc)` while this query wants ascending — exactly the shape a planner quietly abandons, and a sequential scan here stays invisible until the table is large. A spec runs `EXPLAIN (ANALYZE)` over the query the repository actually issued and asserts the plan names the index; wrapping the predicate in a cast turns it red. It seeds 400 rows first, because on a handful Postgres correctly prefers a sequential scan and a spec without data would be asserting the opposite of what it means. The EXPLAIN tooling moved to `infra/db/postgres/test/explain.ts` at the point a second spec file wanted it.

**A route spec must not do heavy real work to reach a cheap assertion.** Two page specs spent their setup on ten real `POST /api/pages` calls, each of which enqueues to a live Redis with a 2s timeout and three retries — so whenever the shared test container was busy the file timed out at 30s rather than failing anything, and the report pointed at rate limiting rather than at the queue. Both now reach the same assertion without the queue: the cap spec seeds pages through the repository and sends one request for the 409 body, and the rate-limit spec spends its bucket on deliberately invalid urls, which is sound precisely because a rejected submission is not refunded. The endpoint behaviour each one asserts is unchanged.


**Three corrections from the #48 review, recorded because two of them invalidate something written above.**

**The row-counting EXPLAIN helper was returning 0 for every input, so the bounded-read assertion above was vacuous.** `EXPLAIN (FORMAT JSON)` yields `[{ "QUERY PLAN": [{ "Plan": … }] }]`, and the walker descended only through `Plan` and `Plans` — it stopped at the first key and never reached a node. "This query reads fewer than sixty rows" therefore held for any query at all. It survived a mutation check because the mutation swapped the lateral for the window function, which also changed the SQL, so the spec's "did we find the query" search failed and went red before the count was ever compared. **A count-based assertion has to be mutation-checked against a change that leaves the query findable** — otherwise the guard passes for the measurement. The spec now sums rows across every query the load issued rather than searching for one, seeds 2,000 audits, and runs `analyze`; the lateral reads 30 and the window function reads 2,001.

**`adaptRoute` was overwriting `Vary` rather than adding to it.** `cors.ts` appends `origin` and carries a comment that overwriting would drop a variant added elsewhere; this adapter was that elsewhere. A controller asking to vary on `Cookie` silently removed `Origin` from the cache key, which on a credentialed CORS response means a cached body can be served to the wrong origin. `Vary` is a list and is now appended; `cache-control` is a single directive set and is still replaced, because a controller opting into caching has to beat the global `no-store` rather than accumulate beside it.

**Five `as Controller` casts are gone, replaced by one that can be justified.** `Controller.handle` is a property rather than a method, so `strictFunctionTypes` checks its parameter contravariantly and `Controller<AddPageRequest>` is not assignable to `Controller<unknown>` — every factory silenced that with a cast it had no way to account for. `adaptRoute` now takes the request type as a parameter, which moves the single unavoidable assertion to the only place that can explain it: the object really is assembled at runtime from a body, a query string and a params bag the framework types as `any`, and every controller re-validates what it reads. Casting at five call sites was hiding one honest boundary.

## 2026-07-29 — the pages API, and what makes a ten-page cap actually a cap

**`POST /api/pages` is one transaction, and it opens by locking the account's own row.** The endpoint does four things — find or create the `Site` for the host, check the cap, insert the `Page`, write its first audit — and they are only correct together. Counting pages and then inserting is check-then-act: under READ COMMITTED two concurrent adds both see nine, both insert, and an account allowed ten holds eleven. `select … for update` on the user row is what closes it. Serialising per account costs nothing real — adds are rare and the cap bounds how long one can take — accounts never contend with each other, and it is the only lock taken, so there is no acquisition order to deadlock on. A spec fires three adds at a two-page account and asserts one `added` and two `limit-reached`; removing the lock turns it red immediately.

The alternative was a unit-of-work abstraction threaded through several repositories, which the #10 review explicitly said not to build speculatively. Putting the whole operation behind one repository method keeps the transaction an implementation detail of the adapter, and keeps the database handle out of every other layer.

**The enqueue happens after the commit, and a failed enqueue does not undo the page.** A job handed to Redis inside a transaction that then rolls back points at nothing. Afterwards there are three outcomes rather than two: queued, definitely-not-queued, and *unknown* — Redis may have committed the job and lost the reply. Only the middle one cleans up. Deleting the audit row on `unknown` would leave a job pointing at a row that no longer exists, which is the failure the retry was supposed to avoid. When it genuinely fails the page stays and the audit row goes: refusing to track a page because Redis blinked is the wrong trade, but a queued row nothing will run renders as permanently in progress.

**`sites.domain` stores the host, not the registrable domain, despite the issue saying otherwise.** Extracting a registrable domain correctly needs the Public Suffix List — a two-label heuristic files `a.co.uk` and `b.co.uk` under one site called `co.uk`. That is a dependency with a data file that goes stale, bought for a column with no behaviour attached: the cap is per account, #13's scheduler and #41's politeness lock both key on host, and alerts are per page. The first genuine site-level feature can add the PSL then, behind a port in `infra/`, where the runtime belongs.

**Two 409s that mean different things carry a `code`; `error` still means what it means everywhere else.** The issue sketched `{ "error": "page_limit_reached", limit, message }`, which would make `error` a machine token on this endpoint and a sentence on every other one, breaking any generic client handler. `codedConflict` sends both: `code` to branch on, `error` to show. Duplicate-before-cap is deliberate in the same spirit — an account at exactly ten re-adding a page it already tracks is told the useful thing rather than sold an upgrade it does not need.

**Limit, then authenticate, then handle — and that order is not what `router.use` gives you.** The auth middleware looks a session up before rejecting it, so a limiter behind it lets an unauthenticated caller drive one indexed query per request, unbounded; `/me` has been wired limiter-first since #10 for exactly that reason. Registering auth once as `router.use('/pages', …)` above four routes that each carry their own limiter reads as if it does the same thing and does the opposite, because Express runs layers in registration order — the prefix `use` wins wherever the limiters are written. It shipped that way in #11's first cut and the review caught it. The fix keeps both properties by making the trio one helper: a route cannot get a limiter without auth, or auth without the limiter in front of it. The spec that catches a regression asserts that an anonymous caller eventually gets `429` rather than `401` forever — the wrong order answers `401` indefinitely and looks perfectly healthy.

**Ownership is a property of the statement, not a check a caller performs.** Every mutating repository method takes `(pageId, userId)` and scopes through `sites`, and there is no single-argument `loadById` to reach for by accident. Cross-account access is `404`, never `403`, because a `403` confirms the row exists and turns id enumeration into an inventory of other people's monitored pages. Ids from a url path are pattern-checked before they reach a query for the same reason `public_uuid` is: a `bigint` column *raises* on a malformed comparison rather than matching nothing, so without the guard `/api/pages/abc` would be a 500 that a prober can tell apart from a 404.

**"No N+1" is asserted as the property it is, and so is "bounded".** The read is a fixed number of queries, and the spec pins that the count for ten pages equals the count for one — not that it equals three, which may legitimately change. Rewriting the latest-audit lookup as a per-page loop turns it red.

The history query took two attempts, and the difference is worth recording because the first one *looks* correct. A plain `limit 30` cannot work at all: over a multi-page result it truncates at whichever pages sort first, leaving later ones with no sparkline. `row_number() … where rank <= 30` fixes that and returns exactly thirty rows per page — Postgres 15 and later even push the comparison into the `WindowAgg` as a `Run Condition`, which is easy to read as "so it stops early". It does not. Measured on Postgres 17 with 3,000 finished audits per page, the index scan underneath still read all 30,000 rows and touched 397 buffers to return 300. A `LATERAL` join asking for thirty rows per page reads thirty — 34 buffers for the same result — and stays there as history grows. With one caveat found later, in #48's review: that win needs the planner to have real statistics. Against a bulk-loaded table with none, Postgres estimates one row, picks a bitmap scan under a top-N sort, and reads everything from the lateral too — so the lateral does not GUARANTEE the bound, it makes it available. Production has statistics from autovacuum; a spec that bulk-inserts has to `analyze` before measuring. On a nightly monitor that is the whole point: the dashboard is the polled endpoint, and its cost must not track how long the account has been a customer. Pinned by a spec that runs `EXPLAIN (ANALYZE, FORMAT JSON)` over the query the repository actually issued and counts rows read from `audits`; the window-function version reads 201 where the lateral reads 30. Bounding *output* and bounding *work* are different properties, and only the second one was ever the goal.

**A route spec needs its own IP block, not just its own counter.** Rate-limit buckets live in a Redis every Vitest worker shares, so two spec files each minting a "unique" address from `10.0.0.1` upward hand Redis the same key. This file signs accounts up, so its addresses collided with `account-routes.test.ts` on the `signup` bucket, whose capacity is 3 — and the symptom belonged to neither file: whichever spec ran third failed, somewhere different each run, roughly half the time. Each route spec now takes a `/16` of its own.

## 2026-07-28 — expired sessions are swept, and signup's 409 stays an account oracle

Two loose ends from the review of `main`, recorded together because the answers point in opposite directions: one was cheap to close, and the other cannot be closed by anything short of email delivery.

**Expired sessions are now deleted, hourly, from the worker.** Expiry was already enforced where sessions are read — `expires_at > now()` in the lookup — so an expired row changed no authorisation outcome. It was never removed, though, so the table only grew: one row per login, forever, including for accounts that never come back. Correct and unbounded is still a problem, and the fix has to be a delete rather than a stricter read.

It runs in the **worker**, not the API. The API scales horizontally, so N instances would issue the same delete on the same rows every hour — harmless, since the statement is idempotent and scoped by the database's own clock, but wasteful and hard to reason about. The worker already owns background work and a database connection. It is a plain timer rather than a BullMQ repeatable job on purpose: a repeatable job would make session maintenance depend on Redis being healthy, and the rate-limiting entry's whole argument is that authentication does not. The delete compares against `now()` for the same reason `loadBySessionId` does — with more than one instance the app clocks drift, and a sweeper on the fast one would delete sessions the slow one still considers live. It does not sweep on boot, because a worker in a crash loop would otherwise issue a table-wide delete on every start, which is exactly when the database least wants one. Index `sessions_expires_at_idx` exists for this delete and for nothing else; the session lookup is by primary key.

**`POST /api/signup` still answers `409` for an email that already exists, which is an account-existence oracle, and it is being kept.** Worth stating plainly because it is the one place the careful work on the login path is undone: login returns an identical `401` for a wrong password and an unknown email, and burns a dummy scrypt verify so a stopwatch cannot separate them — and then signup will tell anyone who asks, in one request, whether an address is registered. An attacker enumerates through signup and only then attacks addresses already known to exist.

**Rate limiting does not fix this, and it is important not to file it under "mitigated by #8".** The oracle leaks on the *first* request for any given email, so a limit on how many requests an attacker may make per hour changes the rate of enumeration and nothing about whether it works. Signup's bucket is keyed per-IP only, so address rotation defeats it outright. Adding a per-email signup bucket would not help either — one probe per email is all the attack needs — and would introduce a fresh denial vector, where burning an address's bucket blocks the legitimate owner from ever signing up with it.

The only real fix is to stop the response from depending on whether the account exists: answer `201` either way, create nothing for a taken address, and send mail — either "here is your account" or "you already have one, here is a reset link". That needs a transactional email provider, which is **#15**, and which does not exist yet. Returning `201` before then would be strictly worse than the leak: a user who already has an account would get a success page, no session, and no email telling them to log in instead.

So it is accepted, deliberately and with the cost named, until #15 lands — at which point signup should change in the same commit that makes the change safe. Recorded here rather than left as a comment because the next person to look at signup will see a plain `409` and no reason to think it was ever considered.

## 2026-07-28 — rate limiting, and why Redis is not a hard dependency for auth

A token bucket per key in Redis, one atomic Lua script, in front of the audit and account endpoints. A bucket rather than a fixed window for two reasons: the natural first session on an anonymous audit tool is "try my homepage, then two more pages", which a burst against a slow refill fits exactly; and a fixed window lets twice the limit land in the two minutes either side of a boundary.

The script reads its clock from Redis rather than taking one from Node. With more than one API instance the app clocks drift, and a bucket shared between them would refill at whichever instance ran fast. It is one script rather than a read and a write because two concurrent requests otherwise both see the last token and both proceed — a property asserted by firing twenty parallel consumes at a capacity of five and counting exactly five allowances.

**When Redis cannot answer, the limiter degrades to a per-instance bucket rather than refusing.** Failing closed on the write endpoints was designed first and rejected. It hands an attacker who can make Redis flaky a complete authentication outage, and degrading a Redis instance is plausibly easier than exhausting scrypt CPU across the API — so the mitigation would convert a hard attack into a cheaper one with a larger blast radius. It also expands a dependency's criticality tier by side effect: Redis entered this codebase as a queue, and a rate-limiting decision is the wrong place to quietly make logging in depend on the queue's health. "Cannot measure" does not have to mean "refuse": a per-instance bucket still bounds the scrypt cost that motivated the limit.

What the fallback gives up is only counter-sharing across instances. **A per-IP limit never defended against distributed IP rotation** — an attacker with many addresses defeats it whether the counters sit in Redis or in memory — so falling back loses no class of defence, and the per-email bucket still works against credential stuffing on one account. The in-memory map is bounded and evicts least-recently-used, because an unbounded one would turn the fallback into a memory-exhaustion vector during exactly the outage it exists to survive.

**`trust proxy` is a hop count, never `true`.** The two wrong settings fail in opposite directions and both look like success. Unset behind a proxy, every anonymous user in the world shares one bucket. Set to `true`, any client can prepend a fabricated address to `X-Forwarded-For` and mint a fresh bucket per request, leaving the limiter decorative. A hop count takes the entry the client could not have written. It defaults to 0 — the safe wrong answer, visible immediately in testing.

**The per-email bucket can be used to lock a known victim out of their own account.** `loginEmail` refills at 10/hour while the per-IP `login` bucket sustains 30/hour from a single address, so one attacker on one IP can hold any known email's bucket at zero indefinitely for roughly 11 requests an hour — comfortably inside that address's own per-IP allowance, no rotation required — and the victim gets a 429 before their correct password is ever checked. This is single-source and unattributable to anything but "someone is hammering this one address", and it is inherent to per-email limiting rather than a bug in these numbers: the alternative is no defence against credential stuffing at all, which is the larger risk. Accepted on that basis. The one thing worth naming precisely: the shared bucket is a weak *activity* oracle, not an account oracle — it reveals that someone has been attempting a given address, never whether an account exists behind it, so it does not weaken the guarantee, recorded further below, that a wrong password and an unknown email return identical 401s.

**`AUDIT_API_ENABLED` is deleted rather than defaulted true.** It existed to make "do not deploy this unprotected" mechanical rather than a comment someone might not read. Now that the protection exists, a flag that can still be left off is only a way to ship a dead endpoint, and a second configuration state every future change has to be tested against.

Rejected submissions are not refunded. The behaviour worth having would refund a syntactic rejection, which costs a parse, while charging one that resolved to a blocked address, which costs a DNS lookup — but both return `400`, so a middleware watching the status cannot tell them apart, and making it visible needs an extra field on `HttpResponse`, a refund handle held outside `res.locals`, and an adapter change. Refunding every `400` was the cheap version and is worse: it makes hostname probing free. The anonymous burst is 5 instead of 3 instead, which costs one number and leaves the sustained rate — the actual cost control — untouched.

**A bare per-requester key is not enough to key storage — the bucket it belongs to has to be in there too.** `ipKey`/`emailKey` return the same string regardless of which named bucket called them, and both token bucket implementations key their storage purely on that string, with no visibility into the `BucketConfig` passed alongside it. Without a namespace, `RATE_LIMITS.auditRead` and `RATE_LIMITS.me` — which happen to share a capacity and refill rate — would silently share one counter per address, and `audit` would share a counter with both.

`name` is a required field on `RateLimitRule`, not a wrapper a call site can forget to apply — `makeRateLimit` itself prefixes the key with it before the limiter ever sees it, so a new rule cannot be wired up without picking a namespace. That closes the instance of the bug but not the class: `name` is a bare `string`, so two rules can still collide by typo or copy-paste (e.g. `/me` accidentally reusing `'login'`).

**The class is closed by a runtime assertion over the whole route table**, in `main/routes/rate-limit-namespaces.spec.ts`. A collision is a property of the table, invisible from inside any one route's spec, so that file registers every route module against a recording router and asserts three things about the rules that come back: names are unique, one name never stands for two different `BucketConfig`s, and every name matches a key that actually exists in `RATE_LIMITS`. The third is the one nothing else can catch — renaming a rule to `'signupp'` leaves the other 486 tests entirely green (measured), because the key prefix is still unique and the bucket is still passed by reference; the name has simply stopped describing what it limits. A compile-time enum of names was the alternative and would close uniqueness only, not that drift.

**The concurrency cap is set globally, not per worker process.** `concurrency` on a BullMQ `Worker` bounds one process, so two replicas configured with `AUDIT_CONCURRENCY=3` run six Chromium instances between them — and the number that is supposed to be the cost backstop turns out to depend on a replica count nothing enforces. Each worker now also writes the value to the queue as BullMQ's global concurrency at startup, which lives in Redis and every worker respects. The per-process setting is still passed, so a single process is bounded even if that call never happened. Pinned by a burst spec with two Worker instances that each locally allow one job: with the global limit the peak is one, and the control without it is two — the third mechanism this issue's sketch described, and the only one of the three that a per-IP limit genuinely cannot substitute for.

## 2026-07-28 — the score formula

`score = max(0, 100 − Σ over rules: weight(impact) × min(elements, 5))`, weights `critical 10 · serious 5 · moderate 2 · minor 1`. Fixed in v1 and not configurable, which is the only thing that makes two scores comparable.

**The per-rule cap is the load-bearing part.** Without it, one unlabelled icon repeated 200 times zeroes an otherwise healthy page, and the number stops tracking anything a team could act on. The counts beside it stay uncapped for the opposite reason — the score must not be able to hide the size of the problem, so a rule failing 200 times deducts 50 and still reports 200.

**Unknown severity deducts, at its own named weight.** axe reports `impact: null` for a violation whose checks carry no severity, and the auditor also funnels any severity we do not model to null rather than dropping a real finding. That second path is why excluding nulls was rejected: an axe upgrade introducing a new severity name would silently stop deducting for every violation carrying it, and every page would drift toward 100 with no code change and no error. `UNKNOWN_IMPACT_WEIGHT` is a separate constant from `WEIGHTS.minor`, though both are 1 — writing `?? 'minor'` invites a later reader to decide minor is too lenient and raise it, which would move real minor violations too.

**Duplicated rules are merged, not rejected.** axe returns one entry per rule, so this is defensive — but the cap is per rule, so two entries for one rule apply it twice and can deduct double for a single problem. It merges rather than throwing because scoring runs inside the worker, after the page has been audited and after the violations have already been committed: throwing would convert a scoring nuance into a failed audit and discard real results. The most severe impact wins, because for a regression monitor, understating severity is the worse direction to be wrong in.

The score and the counts come from one merge pass in one function, so the number and the counts printed next to it cannot disagree about what was found.

## 2026-07-28 — the audit API, and what a public payload may contain

`POST /api/audits` and `GET /api/audits/:uuid` — the one-off audit with no signup, and the result behind the public share page.

**Gate 1 parses and resolves.** #7 left the submission-time check to this issue. It parses with `parseAuditUrl` and resolves the hostname, rejecting when any answer is a blocked address — which is what #7's criteria actually require.

It was very nearly syntactic-only. The argument against resolving was that a lookup per request on an anonymous, unlimited endpoint is an amplifier against a resolver we do not control. What changed is the second decision below: with the endpoint off unless explicitly enabled, and #8 required before enabling it, that objection no longer holds. The two are a package — either would be wrong alone.

Gate 2 still re-resolves at fetch time. This check does not replace it and cannot: the answer can change in between, which is the whole reason the worker validates every request. It rejects what is already known to be wrong, fifty milliseconds in rather than thirty seconds.

**Superseded 2026-07-28.** `AUDIT_API_ENABLED` is deleted (see the rate-limiting entry above): the flag's job was to make "do not deploy this unprotected" mechanical until the rate limiter existed to do that job instead. The paragraph below is left as the historical record of why the flag existed and why the per-request DNS lookup was acceptable under it.

**The endpoints are absent unless `AUDIT_API_ENABLED` is set.** Each accepted request costs roughly thirty seconds of Chromium and nothing throttles that until #8. A comment cannot stop a deploy; an unregistered route can. The flag defaults to false — the only optional boolean in the schema that does — and #8 is what makes turning it on safe.

**A failed enqueue deletes the row rather than stranding it.** The insert must precede the enqueue — reversed, the worker can dequeue an id whose row does not exist — which leaves the window where the row exists and nothing will run it. The enqueue is retried three times first, since most failures are a blip; a sustained one deletes the audit and answers `503`. The row was acknowledged to nobody, so removing it strands nothing and the client simply retries.

The retry is only safe because the enqueue is idempotent. A plain `add` mints a fresh job id per call, so a reply lost after Redis committed would leave two jobs racing for one audit — and the recovery path would then delete a row whose job is still queued. The job id is derived from the audit id, and the failure path asks the queue whether it holds the job before deleting anything.

Each attempt is also bounded by a two-second timeout, which is what makes any of this reachable. BullMQ configures its connection to retry a lost Redis forever, so `add` does not reject when Redis is down — it hangs. Measured at five minutes with no resolution, and `enableOfflineQueue: false` does not change it. Unbounded, the request never answers at all and neither the retry nor the delete ever runs.

Deriving it is less obvious than it looks: BullMQ rejects an all-digit custom id (it would collide with the ids BullMQ assigns itself) and also rejects one containing `:`. Audit ids are a `bigserial`, so every one of them is all digits — passing the id straight through made *every* enqueue throw, and the unit tests could not see it because their ids were not shaped like real ones. The prefix is `audit-`, and the specs covering it run against a real Redis.

Two alternatives were weighed and rejected. **Leaving the row `queued`** and deferring recovery to #13 is simplest, and a stranded `queued` row is indistinguishable from one that has not started — but it is the same shape as the stranded-row defects the audit worker spent several review rounds eliminating. **Claiming it and marking it `failed`** reuses the fenced write path and leaves an explanation, but records a failure for an audit nothing ever attempted, fabricates a claim no worker held, and turns a queue outage into a table of failures rather than a clean rejection. The delete is scoped to `where id = $1 and status = 'queued'`, which is what keeps the only delete on this repository from ever removing a real audit. If it fails too, the outcome degrades to a stranded row — the single accepted residual.

**The public payload is built by an explicit mapper, never spread.** `GET` is gated only by an unguessable uuid, and `AuditModel` carries `pageId`, which links to a site and therefore to an account. A spread, or a later `select *`, is exactly how that reaches the wire — so every field is named, and specs at both the mapper and the route assert the forbidden keys are absent. Mutation-checked by putting `pageId` back.

Worth recording a testing trap found while writing those specs: asserting `JSON.stringify(body)` does not *contain* the internal id is worthless when the id is a `bigserial`. A single digit matches by coincidence inside a uuid or a timestamp, so the assertion fails for the wrong reason and would equally have passed for the wrong reason. Both checks compare structurally instead.

**`HttpResponse` gained an optional `headers`.** The global `no-store` from #10 covers every response, so a route could not otherwise opt into caching. A terminal audit is immutable and carries nothing user-identifying, so the share page can be served from a cache; an in-flight one changes on the next poll and stays `no-store`. The controller describes the intent and `adaptRoute` applies it, mirroring how cookies already work rather than inventing a second mechanism.

**Three leaks review found, all in the same family: things that are true of the model but must not be true of the wire.** A URL carrying credentials — `https://alice:secret@example.com/` — survived normalisation, would have been stored, and then handed back by the public result endpoint and cached for an hour. Violations were loaded whatever the audit's status, so a running audit published whatever the current attempt had written so far as though it were the answer, and a failed one published the leftovers of a run that did not complete. And `HttpResponse.headers` forwarded any header a controller named, which would have let one emit its own `set-cookie` without the adapter's security attributes or rewrite the CORS headers the middleware had just set — so it is now allowlisted to `cache-control` and `vary`, the only response metadata a controller legitimately owns.

Worth recording a testing trap found alongside them: asserting `JSON.stringify(body)` does not *contain* the internal id is worthless when the id is a `bigserial`. A single digit matches by coincidence inside a uuid or a timestamp, so the assertion failed for the wrong reason and would equally have passed for the wrong reason. Both checks compare structurally instead.

**The shared DTO package is not built.** #9 asks for the response contract to live where `web/` can import it, because three surfaces consume it — but there is no `web/` and no workspace yet. The types are exported from `presentation/helpers/audit-view.ts` and the move is recorded on #17, which creates the thing they would move into.

## 2026-07-27 — URL safety: the redirect check the issue described does not fire

"Audit any URL" hands anonymous users a server-side request forgery primitive, so this lands **before** #9 opens that path. The endpoint should never exist in an unsafe form, rather than exist and be fixed afterwards.

**The mechanism #7 specified does not work.** It proposes intercepting navigation with `context.route` and aborting on a blocked address, and calls that "the one that matters" precisely because Playwright follows redirects internally. Verified against real Chromium: the route handler fires **only for the first hop**. A `302` to a private address is followed by the browser, surfaces as a `request` event carrying `redirectedFrom`, and is never offered to the handler — so `page.goto` resolves at the private URL with its content in the page. The redirect check, the entire reason that gate exists, was absent from the design describing it.

What works is **taking redirect-following away from the browser**: inside the handler, walk the chain with `route.fetch({ maxRedirects: 0 })`, validate every hop, and `fulfill` only the final response. That also makes the hop cap countable, which `page.goto` does not otherwise expose. The cost is real and worth naming: navigation responses are fetched through Playwright's API rather than by the browser directly.

Owning the fetch means owning its failures too — a lesson the existing tests taught immediately. A refused connection thrown inside the handler leaves the route unanswered, so `page.goto` runs to its full timeout and a fast, accurate "Nothing responded at that address" becomes a slow, wrong "The page took too long to load". Fetch failures are now translated back into matching Playwright abort codes so the original `net::ERR_*` reaches the classifier.

**Every request is checked, not only navigations.** A page can embed `<img src="http://169.254.169.254/latest/meta-data/">` and the worker would fetch it from inside the network. Nothing reaches the user either way — axe reads the DOM, not image bytes — so this is about side effects rather than disclosure, but a GET that changes state still fires. A blocked subresource refuses only itself, leaving a page that innocently references an unreachable internal host still auditable.

Two smaller findings. **`node:net`'s `BlockList` fails open on non-addresses**: `check('not-an-ip')` returns `false`, so relying on it alone would allow anything unparseable. It does correctly catch `::ffff:127.0.0.1`, the IPv4-mapped bypass, which was the thing most worth verifying. And **ports are allowlisted to 80 and 443** — a non-standard port on a public audit tool is a strong signal of an internal service, and Chromium's own unsafe-port list is not a boundary we control.

**DNS rebinding is bounded rather than eliminated.** Resolve-and-pin is the robust answer and is awkward through Playwright, so validation happens inside the navigation path instead. With the guard now running on every request and its resolver cache scoped to a single audit, the window between checking an address and fetching it is milliseconds rather than the process's lifetime. That is a genuine tradeoff, recorded here as one.

Rejections surface as a `failed` audit carrying **`That address can't be audited`** — identical whatever the reason. A message distinguishing "blocked" from "unreachable" would turn the audit endpoint into an internal port scanner.

One testing note worth keeping, because it looks like a shortcut and is not. The fixture server necessarily listens on loopback and an ephemeral port, both of which the real policy refuses. So the *policy* and the *mechanism* are tested separately: every range and port rule is covered by pure specs with no network at all, while the integration specs relax exactly those two conditions and leave every other range enforced. Neither set can be satisfied by weakening the other.

Review then found four ways the guard was narrower than the rule it was enforcing, and the shape is worth naming: each was the right idea applied to some of its cases and not the rest.

**Subresources were checked once and handed to the browser**, which reintroduced the exact bypass this whole design exists to close — Chromium follows a subresource's 30x internally too, so `<img src="http://public/redirect">` landing on a metadata address sailed through. Every request is now walked; navigations and subresources differ only in what aborting *does*, not in what gets checked.

**The resolver cached completed answers for the whole audit**, so an address was validated once and trusted for tens of seconds. That is long enough to answer publicly, flip DNS, and have a later request approved against the stale public answer while Chromium resolves the private one — and it directly contradicted the "milliseconds" bound claimed above. It now coalesces only lookups genuinely in flight together and evicts on settlement, which keeps the saving that matters (a page pulling twenty subresources from five hosts still costs five lookups) without holding anything.

**The blocklist covered the ranges the issue listed and stopped there.** Verified as allowed before being added: `::` (unspecified, reaches a local listener), `100.64.0.0/10`, `192.0.0.0/24`, `198.18.0.0/15`, `224.0.0.0/4`, `240.0.0.0/4`, and — the subtle ones — `2002::/16` and `64:ff9b::/96`, since 6to4 and NAT64 both embed an IPv4 address, so a v6 literal can address `127.0.0.1` without ever looking like it.

**Service workers were left enabled.** `context.route` does not reliably intercept what a service worker requests, so an audited page could register one and issue requests straight past the guard. Blocked at the context, and pinned by a spec that drives a real context rather than reading the options object back and agreeing with itself.

A further round found three more places the guard was narrower than the rule. **`context.route` does not see WebSockets at all**, so an audited page could open `ws://10.0.0.5/` and reach past every address and scheme check; sockets are now refused outright, since nothing an accessibility audit needs arrives over one.

Proving that took three attempts, and the failures are worth recording because each looked like a passing test. A wiring assertion caught deletion of the line but never showed a real socket being refused. Replacing it with a browser test against a real socket server *still* passed with the registration removed — first because a fixed sleep read the page while its outcome was `pending`, so "not open" held for the wrong reason; then, once that was fixed, because **the navigation guard also breaks the upgrade handshake**. Fetching and fulfilling a navigation happens to refuse sockets too, so a test at the audit-context level cannot attribute the block to anything. Measured in isolation: `routeWebSocket` alone gives `closed`, a bare context gives `open`. The test now isolates the mechanism and keeps a control proving the fixture server genuinely accepts sockets. The incidental block is not relied on — it is a side effect of how navigations are served and would vanish the moment that changed. **The NAT64 block covered only the well-known prefix** — RFC 8215's local-use `64:ff9b:1::/48` translates just as well, and `64:ff9b:1::a00:1` routes to `10.0.0.1`; verified allowed before it was added. And **walking the redirect chain replayed the original request at every hop**, so a `POST` that a server had already acted on was sent again, with its body, to each subsequent URL. Browser semantics are now honoured: 303 always demotes to GET, 301 and 302 do so as every browser has for decades, and 307/308 preserve the method precisely because that is what they exist to say. The body-describing headers go with the body.

A further round closed five more gaps and found one that **cannot be closed here at all**, which is worth stating plainly rather than leaving implied by a passing test suite.

Closed: `fec0::/10`, deprecated but still routed on legacy private networks. Following only 301/302/303/307/308 rather than any 3xx carrying a `Location`, since a 304 would otherwise make the auditor issue a request Chromium never would. Catching a malformed `Location`, which threw outside the fetch handler and left the route unanswered — turning an invalid redirect into a full navigation timeout and three attempts instead of one classified failure. Disposing fetched responses, because Playwright retains every body until `dispose()` and the guard now fetches subresources too. And **validating the submitted URL before navigating**, since the route guard is a network boundary and `file:`/`data:` need not produce an interceptable request at all — a `file:///` audit could otherwise read the worker's own disk before the guard saw anything.

**WebRTC** is removed before any page script runs. It is intercepted by neither `route` nor `routeWebSocket`, a data channel needs no permission, and Chromium will send packets to whatever ICE candidate address a page supplies. The removal is non-configurable so a page cannot restore it.

A later round found the redirect walk had broken something ordinary while securing something rare, which is the more expensive kind of mistake. **Fulfilling the final response collapsed the chain onto the first URL**: Playwright copies status, headers and body onto the original request, so `/start` redirecting to `/dir/page` left the document at `/start`, resolved `<img src="asset.png">` to `/asset.png` — a 404 — and ran the target's content under the start origin. Every redirecting site would have audited wrongly, and origin isolation was violated into the bargain. The guard now walks and validates the chain as before, then hands the browser a redirect to the validated final URL and lets it own the document. The cost is one extra fetch of that final URL, by the browser; the alternative was a broken audit.

Three smaller ones alongside it: request bodies are replayed from `postDataBuffer()` rather than `postData()`, which decodes as UTF-8 and corrupts binary and multipart uploads; **WebTransport** is removed along with WebRTC, since QUIC is intercepted by neither `route` nor `routeWebSocket` either; and the IPv6 blocklist now covers IANA's non-global space rather than a hand-picked subset — including **Teredo (`2001::/32`)**, which embeds an IPv4 address exactly as 6to4 does and could therefore name a private host outright.

**Downloads are the one that stays open.** `context.route` does not see them: measured, a programmatic click on `<a download href="http://10.0.0.5/…">` reaches the server with `acceptDownloads: false` *and* with the download event cancelled — Playwright only learns about it after dispatch. `acceptDownloads: false` is set so nothing hostile lands on the worker's disk, but the request itself still leaves. So the "every request is validated" claim is **not true for downloads**, and the honest scope is: every request the page makes through normal navigation, subresource loading or redirect. Closing it needs enforcement below the browser — infrastructure egress policy, which this issue already listed as out of scope and defence in depth. That upgrades it from a nice-to-have to the only thing that closes this, and is recorded on #16.

One tooling note, because it constrains anything that runs in the page. Two functions execute in the browser via `page.evaluate` while being typechecked as part of a Node project, so `document` and the injected `axe` global do not exist to the compiler. Adding `"DOM"` to `lib` would make `document`, `window` and `localStorage` compile throughout the server, and a per-file `/// <reference lib="dom" />` **does not scope per file** — verified: a second file in the same program picked it up with no directive of its own. The only real isolation is a separate compilation unit, which is #38.

Until then the cast stays but is **checked rather than asserted**: the browser body is a self-contained exported function that verifies the engine is present and that its result still has the shape expected, throwing messages the classifier already maps to a permanent engine failure. Being self-contained is also what lets it be driven directly in Node against a stand-in global — the only way to reach those branches, since a real page always has axe injected by the time it runs. `target` and `lib` moved to ES2024, which Node 24 fully provides.

Still deferred: gate 1, the submission-time check, which belongs in #9's `request-audit` usecase and has no home until that exists. It is not redundant once this gate exists — it turns an obviously bad URL into an immediate `400` rather than a queued job, a browser launch and a failed audit thirty seconds later.

## 2026-07-27 — the audit worker: navigate once, audit anyway, and say so

The engine. A BullMQ job takes an audit id, drives Chromium via Playwright, injects vendored axe-core, and records what it found. Four decisions, three of them made by measuring rather than reading.

**A page that never goes idle is audited anyway, and the audit says so.** Analytics beacons, polling and live chat keep the network busy forever, so `networkidle` never fires on a meaningful share of real sites. Failing those audits would make the product look broken on pages that are fine; auditing them silently would be worse, because a clean score from a half-rendered SPA is a lie that reads exactly like success. So `audits` gains a `settled` column: false means the page never finished loading and the result should not be trusted as a complete picture. Rejected: `networkidle` or fail (fails good sites), and `domcontentloaded` always (under-renders client-side apps, which are the pages most likely to have the problems tabstop exists to find).

**One navigation, not two.** The obvious implementation waits for `networkidle` and, on timeout, navigates again with `domcontentloaded`. That loads the page twice — doubling the cost of exactly the slow pages that triggered it, doubling the request load on someone else's site, and risking a different second render from A/B tests or one-shot banners. Navigating once with `domcontentloaded` and then awaiting the `networkidle` load state separately gets the same outcome for one page load.

**Failures are classified, because retrying is not free.** The queue defaults to three attempts with exponential backoff. Applied naively that is wrong twice over: a domain that will never resolve burns three slots of a capped worker pool for the same certain failure, and the audit row flaps `failed → running → failed` in front of the user. A pure `classifyAuditError` decides — DNS failure, refused connection, blocked port, bad certificate, a CSP that blocks the engine and a navigation timeout are permanent and fail immediately; a browser crash or a database blip is retried, and the row is only written `failed` once attempts are exhausted. Anything unrecognised is treated as transient on purpose: a new failure mode is more likely infrastructure than a permanent property of someone's page, and the cost of guessing wrong is three attempts rather than a permanent failure the user cannot retry.

The queue's vocabulary stops at the composition root. The usecase raises a domain `PermanentAuditError`, and only the worker adapter knows to translate that into BullMQ's `UnrecoverableError` and to supply `isFinalAttempt` from `job.attemptsMade`. That is what keeps the whole status machine testable with no queue at all.

**The payload optimisation the issue proposed does almost nothing; the one that matters is different.** Measured on a fixture page: a raw `axe.run()` serialises to 42,996 bytes, and adding `resultTypes: ['violations']` gives 41,922 — a 2.5% saving, not the "dramatic" reduction assumed. `passes` still comes back as 17 full rule entries; the option only trims their node arrays. Mapping the violations **inside `page.evaluate`** and returning just those is 621 bytes, a 67x reduction, because `passes` never crosses the CDP boundary. It also means no axe result type ever exists in Node, so the `PageAuditor` boundary is real rather than nominal — a node carries `target` and `html`, and axe's `any`/`all`/`none`/`failureSummary` are discarded in the browser.

Two things that only surfaced by running it. **`bypassCSP: true` is load-bearing**: without it `addScriptTag` throws "Executing inline script violates the following Content Security Policy", so we would fail on exactly the sites most likely to have been built carefully. And **timeouts must be identified by `error.name`, not by class**: Playwright's bundling makes the timeout's `constructor.name` `TimeoutError2` while `error.name` stays `TimeoutError`, so an `instanceof` check silently never matches and every timeout would be retried three times before failing.

Also decided: Chromium launches lazily and is reused for the process's lifetime while a fresh **context** is created per audit — the context is the isolation boundary, and launching per job costs about a second plus heavy memory churn. `AUDIT_CONCURRENCY` defaults to 1 because Chromium is 300–500MB per context; #8 owns raising it once #16 has sized the instance. The audit job runs in the existing worker process as a second BullMQ `Worker` rather than a new deploy unit, and that process now connects to Postgres, which the ping-only worker never needed.

Review surfaced three defects worth recording because each defeats a decision above rather than merely being a bug. The shared browser was cached with `??=` **after** an await, so concurrent first audits each launched their own Chromium — measured at three launches for three callers, orphaning two — and a crashed browser stayed cached, so the deliberately-retryable "browser crashed" failure could never actually succeed on retry. Caching the in-flight promise and checking `isConnected()` fixes both. Second, persistence was two separate non-idempotent writes: a queue redelivery after violations committed but before the audit was marked done would insert the same rules twice, and `violations` has no uniqueness constraint to catch it — so the write is now a single-transaction `replaceAll`, the append-only `addMany` is gone rather than left as a trap, and an audit already in a terminal state is skipped outright. Third, the user-facing timeout message named a hardcoded 20 seconds while the budget is configurable; it is now duration-neutral, because the classifier has no business knowing the configuration.

A second review round found three more, each undoing a guarantee rather than merely misbehaving. **The job timeout settled the moment its signal fired**, so BullMQ was free to begin the next attempt - and shutdown free to close the shared browser and the pool - while the abandoned attempt was still closing its context and writing its status; a late write then landed on top of the retry. `runWithTimeout` now waits for the handler to finish unwinding before reporting the timeout, bounded by a grace so a handler that ignores its signal cannot stall the worker. **The replacement transaction was atomic but not serialised**: under READ COMMITTED two concurrent attempts both delete zero rows and both insert, duplicating everything the idempotency was meant to prevent - so the parent audit row is locked first. And **violations that axe reports with no severity were being dropped entirely**, which would mark an audit `done` while omitting real findings; `violations.impact` is now nullable and such rows are stored but left out of the impact counts, because inventing a severity would corrupt the comparison regression detection makes between audits.

A third round found two more of the same character. **Skipping a finished audit was a check followed by a write**, so another delivery could complete the audit in between and this one would resurrect it into `running`, letting a later run overwrite the result. Claiming is now a single conditional update — `set status = 'running' where id = $1 and status in ('queued','running')` — which both refuses terminal states and keeps an audit stranded in `running` by a dead worker retryable. **And `void promise` discards the value, not the rejection**: a `context.close()` that rejects because the browser already crashed became an unhandled rejection, which Node 24 treats as fatal — killing the worker instead of letting the job retry, in exactly the crash-recovery path the transient classification exists to serve. Verified by watching the process die. The fire-and-forget closes now carry rejection handlers, while the awaited close in `finally` still reports genuine cleanup failures.

A fourth round found four more, all of them cases where a rule was right but its predicate was too coarse. **Claiming on `status in ('queued','running')` was not mutual exclusion at all**: under READ COMMITTED a second delivery re-evaluates the predicate after the first commits, matches the row it just claimed, and both run Chromium against the same audit before overwriting each other's metadata. Status cannot distinguish "another worker has this right now" from "a worker died and left it here", and those need opposite answers - so the claim now carries a lease in `audits.claimed_at`: a claim younger than the lease excludes everyone, an older one is reclaimable. **A `TimeoutError` was assumed to be a navigation timeout**, but `chromium.launch()` raises the same error name, so an unhealthy worker host would permanently fail an audit for a problem that is ours; the mapping is now scoped to `page.goto`. **The engine-failure pattern matched a method prefix**, so `page.evaluate: Target page, context or browser has been closed` - a mid-run browser crash, deliberately retryable - was being classified as permanently broken; crash and closure patterns are now checked first. And **axe does not always return a flat selector list**: a node inside a shadow root arrives as `[["#host","input"]]`, verified, so the `string[]` annotation was a runtime lie that jsonb would happily store. Nested selectors are flattened in the browser using Playwright's own `>>>` notation, which keeps the type true and still reads as a selector path.

The lease then produced a defect of its own, which is the sharpest lesson in the sequence: **a retryable failure writes no terminal status, so the row kept a live claim**. The queue's retry arrives after a one-second backoff, far inside a ten-minute lease, fails to claim, finds nothing to do, reports success - and the audit is stranded in `running` for ever with no result and no error. Every transient failure would have silently lost its audit. The fix is to hand the claim back before rethrowing, fenced on the claim's own timestamp so an attempt that has already been superseded cannot release a claim it no longer holds, and conditional on `running` so a finished audit is never dragged back to `queued`. Covered end to end against the real repository: a failed attempt, then a retry that claims and completes.

The lease produced two further defects of its own, both from treating a derived quantity as a chosen one. **Ten minutes was not actually longer than an attempt can last**: it looked generous against the 45s default and was shorter than the 600s maximum the environment schema permits plus its 15s unwind grace, so a valid configuration let a second worker reclaim a still-running audit. The lease is now computed from the configured budget plus that grace plus a clock-skew margin, so raising `AUDIT_JOB_TIMEOUT_MS` raises it automatically. **And a failed claim was treated as successful job completion**, which is right for a finished audit and wrong for one still held: the attempt holding it may yet die without writing a terminal status, and an acknowledgement here means nothing ever picks the audit up again. The two cases are now distinguished, and a held audit fails so the job stays on the queue.

Fencing the release but not the writes turned out to be half a fix. **Every write that finishes an attempt now carries the claim token** - `markDone`, `markFailed` and the violation replacement alike - because an attempt that paused past its lease can resume after another worker has reclaimed and completed the audit, and an unfenced write would overwrite the new owner's result, turn a success into a failure, or swap in a stale set of violations. Ownership is checked inside the replacement's transaction while the audit row lock is held, not before taking it. A write from an attempt that no longer owns the audit is dropped silently, which is the correct outcome rather than an error: the owner's result is the authoritative one.

The last of it was configuration. **The audit budgets were validated independently although they nest**, so `AUDIT_NAVIGATION_TIMEOUT_MS=600000` under the 45s job budget passed every individual check and could never be reached - the job aborts first, making both the navigation budget and the specific, actionable message mapped to it dead configuration. `parseEnv` now rejects any combination where navigation, settle, fallback and execution headroom do not fit inside the job budget.

One test had to be rewritten rather than a behaviour changed, and it is worth recording because the failure mode is easy to repeat. The end-to-end redelivery test asserted that replaying a completed audit did not duplicate its violations - which was meaningful when written, and became **vacuous the moment the ownership fence landed**: the audit is `done` by then, so the replay is a no-op and the assertion held even with replacement entirely removed. Verified by deleting the delete and watching it still pass. It now reproduces the actual interruption - an attempt that commits violations and dies before writing a terminal status, followed by a retry that runs to completion - and asserts the crashed attempt's row is gone rather than sitting alongside the new ones. The general lesson: adding a guard can silently neuter tests written before it, so a mutation check belongs on the tests *near* a new guard, not only on the test that accompanies it.

Finally, the vendored `axe.min.js` needs an explicit copy step in `pnpm build`: `tsc` compiles `.ts` and ignores everything else, so the engine would never reach `dist/` — a failure that appears only in production. A spec asserts the built file exists, and CI builds before testing so that assertion is not vacuous.

## 2026-07-26 — accounts: an opaque session cookie, stdlib scrypt, and a domain we now have to own

Signup, login, logout and `GET /api/me`, plus the `sites.user_id` foreign key #4 deferred. Three decisions, and one obligation they create for deploy.

**The session is an opaque id in an `httpOnly` cookie, backed by a `sessions` table.** Rejected: a **JWT in the cookie**, because logout would only clear the client's copy — a token that had been copied stays valid until it expires, and real revocation then needs a denylist, which is the `sessions` table inverted plus a library and a secret to rotate. Rejected: a **bearer token** in `Authorization`, the reference template's pattern, because it puts the credential where JavaScript can read it. That matters more here than in most apps: `Violation.nodes[].html` is markup captured from arbitrary third-party pages and rendered in our UI, so this product carries a live XSS surface by design. The cost is one indexed lookup per authenticated request, on routes that already query the database.

**Passwords use `node:crypto` scrypt, not argon2 or bcrypt.** Both alternatives are native modules needing a prebuilt binary or `node-gyp` per platform and Node ABI — across macOS development, CI, and a deploy image already carrying Playwright and Chromium. scrypt is memory-hard, cost-tunable, and already in the runtime. bcrypt would additionally have needed an explicit length cap, since it silently truncates past 72 bytes. Zero dependencies added, consistent with hand-rolling `cors` and skipping `dotenv`.

**Parameters are N=32768, r=8, p=3** — OWASP's `2^15/8/3`. Worth spelling out why, because the obvious reading of the guidance leads somewhere bad: OWASP publishes a set of equivalent configurations rather than one N, and `2^15/8/1` is not one of them. But the headline `2^17/8/1` is the wrong correction here — scrypt's memory is `128 · r · N` and is independent of `p`, so `2^17` costs 128 MB per hash, roughly 512 MB across Node's default four-thread pool under concurrent logins. With rate limiting still deferred to #8, that would swap a cracking-resistance gap for a live memory-exhaustion vector. Raising `p` instead buys the same CPU work at an unchanged 32 MB footprint: 86 ms → 236 ms, same memory.

The digest is self-describing — `scrypt$N$r$p$salt$key` — so the cost can be raised later without a migration and without invalidating stored passwords. Two things that only surfaced by running it: Node's default `maxmem` **rejects any cost above N=16384** at runtime with `Invalid scrypt params`, and `timingSafeEqual` **throws on unequal-length buffers**, so the candidate key must be derived at the stored digest's length rather than at a constant — otherwise verifying an old-cost digest crashes instead of returning false.

**Validation parses with zod behind a `Validation` protocol.** `server/README.md` had recorded that no validation layer existed until something real needed one; signup is that thing. The deciding argument was not line count: a validator returning `Error | null` leaves the controller holding `unknown` and casting it, and under this repo's `strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` settings that cast is an unchecked assertion that merely looks like verification. zod parses, so the typed value is earned. Two constraints keep it honest — the protocol returns the parsed data rather than just an error, and zod is imported in exactly two files so no library type reaches `domain/` or `data/`. A gotcha worth keeping: `z.email().transform(v => v.toLowerCase())` looks like it normalises and does not, because the format check runs first and rejects surrounding whitespace before anything can trim it. The correct form is `z.string().trim().pipe(z.email())`.

**The cookie decision commits us to a domain, and that is a deploy prerequisite rather than a preference.** `SameSite=Lax` sends the cookie only on same-*site* requests. If the frontend and API were served from different registrable domains, the session cookie would become a third-party cookie — **Safari blocks those outright** (ITP, default since 2020), as does Chrome Incognito and any user with tracking protection. Login would appear to succeed while nothing was ever authenticated. `SameSite=None; Secure` does not rescue it, since third-party blocking is independent of CSRF, and betting a login flow on the `Partitioned`/CHIPS attribute behaving in Safari is not a bet worth taking for an accessibility product whose users skew toward Safari and VoiceOver. So `app.<domain>` and `api.<domain>` must share a registrable domain; the hosting providers stay independent. Recorded on #16.

Two smaller calls. **`409`, not the template's `403`, for a duplicate email** — `403` means "we know who you are and you may not", and signup is unauthenticated. And **`FRONTEND_ORIGIN` and `SESSION_COOKIE_SECURE` are required, not defaulted**: defaulted to `false`, production ships insecure cookies if anyone forgets; defaulted to `true`, local login fails silently over http. Neither failure announces itself, so the variable is mandatory — the same fail-fast-on-bad-configuration reasoning already applied to `DATABASE_URL`.

**The session cookie is named `__Host-sid`, and the name is doing work.** Browsers refuse a `__Host-` cookie unless it is `Secure`, `Path=/` and has no `Domain` — which makes the name unusable by any other host. That matters precisely because of the decision above: putting `app` and `api` under one registrable domain means sibling hosts exist by design, and without the prefix any of them could set `sid` with `Domain=.example.com` and silently switch a victim into the attacker's session, with logout revoking the attacker's id rather than the victim's. Host-only attributes stop the cookie leaking *to* siblings; only the prefix stops one being injected *from* them. Local http development falls back to the bare name, where no sibling exists.

Also worth recording, because both are invisible until they are exploited: the login path **runs a scrypt verify against a dummy digest even when the email is unknown**, since otherwise an unknown email returns in ~0ms and a known one in ~89ms and the deliberately identical error message is undone by a stopwatch. And `adaptRoute` merges `res.locals` **last**, after the request body, so a client cannot post `{"userId": ...}` and impersonate — a spec pins that ordering, and reversing it fails the spec.

Two smaller hardening calls fell out of review. Every response carries `Cache-Control: no-store` — `GET /api/me` returns per-user data, and a 200 without it is heuristically cacheable by the CDN #16 will put in front of the API, which could then serve one user's identity to another. And `SCRYPT_COST` is validated at boot as a genuinely usable scrypt cost rather than merely a positive integer: `20000` is an integer above zero that makes every hash throw, which would have broken signup with a 500 while login carried on working from stored digests — the sort of partial breakage the fail-fast configuration rule exists to catch.

**Signup is deliberately not transactional, and that is a judgement rather than an oversight.** The account row commits before the session is created, so a session insert that fails leaves an account behind and answers 500. The outcome is recoverable rather than a lockout: the account carries the user's own password digest, so logging in works immediately and issues a session — only a *second signup* would meet a 409. Making it atomic needs a unit-of-work abstraction spanning two repositories, which is real structure to introduce for a window that opens only if the database fails between two statements in the same request. #11 brings the first genuine multi-write usecase (create site, create page, enqueue an audit), and that is where a transaction boundary earns its place; recorded there rather than built speculatively here.

Deferred, each recorded on the issue that inherits it: login rate limiting (#8), the expired-session sweep (#13), `credentials: 'include'` in the API client (#17), and the cross-account `404` criterion (#11, since `/api/me` returns your own user and offers no cross-account case to test). Email verification, password reset, OAuth, teams and roles remain v2.

## 2026-07-26 — the schema, and four things the issue got wrong

Five tables — `sites`, `pages`, `audits`, `violations`, `alert_events` — in one migration. Domain models stay camelCase and persistence-free; repositories own the snake_case translation, matching the constructor-injection decision from the Postgres wiring entry below.

**Anonymous audits are the product's hook, so `audits.page_id` is nullable.** A one-off is an audit with no page, addressed by an unguessable `public_uuid` that is separate from the `bigserial` primary key: internal joins stay cheap, and the world never sees a sequential id it could enumerate.

Four corrections to the shape the issue proposed, all found by running it rather than reading it:

1. **The daily alert dedupe index could not be created at all.** `(page_id, (emailed_at::date))` is rejected — casting a `timestamptz` to `date` is STABLE, not IMMUTABLE, because it depends on the session `TimeZone`. Pinning the zone fixes it, and makes the dedupe window explicitly a **UTC** day.
2. **The dedupe was keyed on the wrong column, and `emailed_at` was not nullable.** Regression detection records an `AlertEvent`; sending the email is a separate, later step that must set `emailed_at` only on a confirmed send and leave it null when delivery fails — otherwise the send job cannot find the alerts it still owes. A `not null default now()` marked every event as already delivered the moment it was created, making retries impossible.

   Simply making the column nullable would have been worse than the original bug: **NULLs never collide in a unique index**, so the dedupe would have silently permitted unlimited duplicate alerts for exactly the unsent rows it exists to catch — verified, three unsent alerts for one page all accepted. So `alert_events` now carries a separate `created_at`, and the dedupe keys on that. That is also the right meaning: whether a page has already alerted today is a fact about detection, not about whether an email provider happened to accept the message.
3. **`counts_by_impact` defaulted to `'{}'` while the domain type declared `Record<Impact, number>`** — so every queued audit would have violated its own type. The default is now all-zeros, and a check constraint (`?& array[...]`) makes the type true by construction instead of by convention, since jsonb enforces no shape of its own.
4. **jsonb writes must be stringified.** node-postgres serialises a plain object as JSON but an array as a Postgres array literal, which the jsonb parser rejects. So `counts_by_impact` would have worked and `violations.nodes` would have failed at runtime — the worst kind of half-truth. Every jsonb column is typed to require a string on insert, which makes the compiler enforce it. Worth knowing for specs too: jsonb does not preserve key order, so jsonb values must be compared structurally rather than as serialised JSON.

Also decided: deleting a page **cascades** to its audits, violations and alert events, which means its public share links stop resolving. That is the intended privacy behaviour — a user who deletes a tracked page should not leave working public URLs exposing that page's failures. `alert_events.previous_audit_id` is the one exception, `on delete set null`, because an alert is about its *current* audit and must survive retention deleting the older one it compared against.

Scope deliberately left out: repositories for `Site`, `Page` and `AlertEvent`. They have no caller until the pages API and regression detection exist, and a query shape written months before its first use is written against a guess — the same reasoning that kept a queue singleton out of the job-runtime work. The obligations were recorded as comments on the issues that inherit them rather than only here.

## 2026-07-26 — background jobs run on BullMQ, and Redis is the price

Audits take ~30 seconds of real compute, so they cannot run inside an HTTP request. `POST /api/audits` will return 202 and hand the work to a BullMQ queue consumed by a separate worker process.

Rejected: **pg-boss**, which is Postgres-backed and would have added no new infrastructure at all — the strongest argument on the table, and declined deliberately. **Graphile Worker**, also Postgres-backed, but still 0.x and it pulls a config/CLI surface this project does not need.

Why BullMQ anyway: it is the most widely used Node queue, and on a solo-operated product the ability to reason about the queue at 2am outweighs one fewer service to run. Its concurrency and rate-limiting primitives are also the most mature of the three, which matters directly for the audit worker's cost controls.

**Redis is accepted knowingly as a second datastore.** That is the cost of this choice, and it lands on local development, CI, and deploy. Recording it here because "why not the Postgres-backed one, when Postgres was right there" is the obvious question to ask of this repo later, and the answer should not be that nobody considered it.

Also decided: no `queue` field on `/api/health`. A health endpoint that fails because a dependency is unreachable is a deep health check, and its failure mode is correlated — Redis blips, every instance reports unhealthy at once, and a partial degradation becomes a total outage. The same critique applies to the `database` field already shipped, and revisiting it is deferred to the deploy issue, where the platform's actual restart and readiness semantics are known rather than guessed at.

Two implementation notes worth keeping: BullMQ has no per-job timeout of any kind, so handlers supply their own via an `AbortSignal` that is passed into the handler rather than raced around it — otherwise a timed-out job leaves its work running. And `lockDuration` defaults to 30 seconds while an audit takes about that long; automatic lock renewal is the only reason the default is safe, so the audit worker should set it explicitly rather than inherit it.

## 2026-07-25 — Postgres via Kysely, wired behind constructor injection

Kysely (query builder over `pg`) is the database client, wired into `server/` behind protocols in `data/protocols/db/`. Proven by a reachability probe on `GET /api/health`; no application tables exist yet.

Why Kysely: it returns plain objects, so mapping to domain models at the infra boundary stays explicit and persistence types cannot quietly become domain types. Rejected: Drizzle (its inferred row types are convenient enough that skipping the mapping becomes tempting), raw `pg` with hand-written SQL (nothing verifies the declared row type matches the query), and Prisma (a generated client plus query-engine binary is the hardest to hide behind a protocol, and adds a codegen step to CI and to the worker image that already carries Playwright).

Two deliberate departures from the reference implementation of this template, [georgekaran/survey-server](https://github.com/georgekaran/survey-server):

1. **Constructor injection, not a static helper.** `AccountMongoRepository` calls `MongoHelper.getCollection()` from inside itself — a service locator, which hides the dependency and needs global state in tests. That was justified there because `getCollection()` carries lazy-reconnect logic and had to be reachable from within the repository; `pg`'s pool reconnects internally, so a Kysely instance is an inert handle that can simply be passed in. The singleton lives in `main/config/database.ts`, where wiring state belongs.

2. **A dead database degrades rather than prevents boot.** `survey-server` chains `connect().then(listen)`, so a failed connection means nothing ever listens. Here the process starts and `/api/health` returns 503 with `database: "down"`. Since the deploy health check will point at that endpoint, an honest 503 stops traffic being routed while keeping the container alive and its logs readable. Missing `DATABASE_URL` is still fatal at boot: bad configuration should fail fast, unreachable infrastructure should not.

Manual verification turned up a defect in that second decision: `pg.Pool` emits an `'error'` event for idle clients when the backend terminates them (Postgres code `57P01` — a database restart, or an operator dropping the connection), and with no listener attached, Node treats that as fatal and kills the process. That's the exact scenario the degrade-don't-die decision exists to handle, so the one case it was meant to survive was the one crashing the server. The whole suite was green and typecheck was clean the entire time this was broken — it only surfaced by actually killing a connection and watching what happened. Fixed with a log-and-swallow `pool.on('error')` handler in `makeDatabase`, covered by a regression spec that terminates a backend via `pg_terminate_backend` and asserts the process survives. Graceful shutdown also closes idle connections up front and carries an `unref()`'d 10-second force-exit backstop that exits non-zero, so a drain that hangs can't silently skip closing the pool.

Also decided: migrations are registered in a typechecked object literal rather than discovered by `FileMigrationProvider`, whose `__dirname`-relative resolution differs across `tsx`, `dist/`, and Vitest under `"type": "module"`. Integration specs get a real database from Testcontainers via Vitest `globalSetup`, so `pnpm test` needs Docker and exercises migrations on every run.

Still deferred: the job runtime, email delivery, and the audit worker's integration into the layered structure.

## 2026-07-18 — the score is for trending, not judging

axe-core deliberately doesn't produce a score, so ours is opinionated: weighted deductions by impact, per-rule element counts capped so one repeated unlabeled icon can't zero a page. Raw counts by impact are always shown next to the score.

Why: a single number is what makes *regression* visible at a glance; the violation list is what makes fixing possible. Conflating the two is how scores get gamed or dismissed.
